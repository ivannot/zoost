Try it on invented data

Both extensions can write a workspace of made-up data into a folder you choose, and then work on it exactly as they would on a real one. No Zoho account, no sign-in, no permission granted to anything.

Every other page here argues that Zoost is worth trusting. This one hands you the means to decide for yourself, which is a different and better thing. Install the extension, press one button, and the whole product is in front of you - the tree, the search, the diagrams, the health audit, the exports, the assistant - running on a workspace that came from nowhere near your company.

What gets written

The button is + Sample, in the workspace bar. It creates one folder inside your working folder and fills it with files in the exact shape a real pull produces. Nothing is downloaded, because there is nothing to download from.

The names are ordinary business words - buildInvoice, calcTax, Contacts - and Zoho's own module names where a module name is needed. There is no real portal, function or field name anywhere in it, which matters because this project claims to be built independently of anyone's day job and a real name in a fixture would quietly contradict that.

Why this is a security argument, not a convenience

A sample workspace is the only way to answer "what does this thing actually do" without first giving it something to read. That order is usually the wrong way round: you install, you grant access to the org, and only then do you find out. Here you can look first.

What holds while a sample is open:

  • Nothing is fetched. The files are generated in the browser and written to your disk. No request goes to Zoho, and none goes anywhere else.
  • Everything platform-bound is refused, in one place in the code rather than by a check repeated at each button - guardOk(), which every such action already asks. Pull, per-item refresh, "open this in Zoho": all disabled, with the reason stated rather than left to be worked out.
  • There is no demo mode. The flag sample: true in the workspace's config is the entire mechanism. Once the files are on disk they are read by the ordinary code, listed by the ordinary list, exported by the ordinary export. A branch that showed invented data differently would eventually show somebody's real data through it.
  • Deleting it is deleting the folder. The one trace outside it is the sample's own identifier, kept in the browser's local storage so the panel can offer to open it before Chrome has granted access to the folder again. The privacy page lists that alongside everything else the extension stores.

And the sample says what it is, everywhere it appears. If a Zoho tab is open on a real organisation while you are reading invented data, the panel states the discrepancy in the workspace bar instead of letting the two blur. It does not block you - a sample will never match any organisation, so blocking would make it unusable - but it will not let you forget.

If you are the one approving the install

You can run the whole evaluation yourself, on a machine with no Zoho session at all, and answer the questions that usually have to be taken on faith: what it reads, what it writes, where the files go, what leaves the machine, what the exports contain, what the assistant is told. The nerd page covers how a release is built and how to verify the package you install is the one built from the published source; this page is the other half, and the two together mean an approval can rest on something you saw rather than something you were told.

One thing to have straight before you start: the optional AI assistant is the only feature that sends anything anywhere, and it stays off until you enter your own API key. It does work on a sample, which is the point - you can evaluate that part too, and what leaves the machine is invented. Pointed at your own organisation the same feature sends real Deluge source to the provider you configured, and that trade is set out on the privacy page.

How to do it

  1. Install Zoost CRM or Zoost Analytics from the Chrome Web Store, and open the side panel from the toolbar.
  2. Choose a working folder when the panel asks. Anywhere will do; an empty folder is tidiest. Chrome asks for permission on that folder and on nothing else.
  3. Press + Sample. It writes the files and opens the workspace. On a machine with no Zoho tab open the same button is on the panel's front screen, because that is exactly where someone who has just installed it will be.
  4. Use it. Every part of the product works: search across all the sources, the call graph and the entity-relationship diagram, the health audit with its stated coverage gaps, and both exports.
  5. Delete the folder when you are done.

The panel will not create a second sample. If one already exists the button reads Open sample workspace and opens the one that is there - and before Chrome has granted the panel access to the folder it says neither, because at that moment it has not looked and neither claim would be warranted.

What it does not prove

An invented organisation is not yours. It will not tell you how long a pull takes against a portal with three thousand functions, whether your role can read the connections catalogue, or what the diagrams look like at the size your organisation actually is. It is deliberately built to contain one of everything - including the awkward states, like a module Zoho refuses to describe - so what you see is the product at its full complexity rather than a tidied version, but complexity is not scale.

What it does answer is every question about behaviour, and those are the ones that decide whether something is safe to install.

The generator is sample-org.js in each extension, and it ships inside the package - so it is readable in the source you install, and the same file is what writes the fixtures the tests run against. Two consumers, one description, which is why the sample cannot drift from the shape a real pull produces.
