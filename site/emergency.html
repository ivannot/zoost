In case of emergency

Zoho changes something undocumented, part of Zoost stops working, a fix goes out the same day - and then it sits in a review queue for days. This page is how you skip the queue and run that fix now. It is the same signed package the Chrome Web Store is given, installed by hand.

What is where, right now

This block is filled in when the page loads, by asking the Chrome Web Store what it is serving and GitHub what has been released. If the two agree there is nothing here worth doing: install from the Store like everybody else.

If this stays as it is - no script, or the check could not run - the releases page lists what exists, and each product's Store listing states what it is serving.

Nothing on this page decides for you. It shows the two version numbers and what changed between them, and you judge whether it is worth the trouble. A fix for something you have never hit is not an emergency.

Why the fix is quick and the queue is not

Zoost is written and maintained by one person. Assessments of this project keep naming that as its main risk, and they are right to: there is no team, no rota, and nobody to hand it to. Here is the other half of it, stated as structure rather than as a promise.

Both extensions run on interfaces Zoho does not document. Zoho can change one without notice, and when that happens some part of Zoost stops working. That is the failure this page exists for. What follows a break is short: there is nobody to coordinate with, no release train to catch and no sprint boundary to wait for, so a small fix can be understood, written, tagged and built on the day it is reported. What takes days is the review queue at Google, and nobody here can shorten it.

So the shape of it is: the repair is fast, the delivery is slow. This page is how you skip the slow part on the occasions when it actually costs you something.

None of that is a commitment. The licence says AS IS and means it. There is no guaranteed response time, no support obligation, and no promise that any particular break will be fixed at all. What is described above is where the time goes, not how much of it you are owed.

And the honest answer to the question behind the criticism, which is what happens if he stops: your mirror is plain files on your own disk. Deluge sources, SQL, JSON and Markdown, readable with a text editor and a Git client, and they stay readable whether or not Zoost is ever updated again. The source is Apache-2.0, releases are built in public and signed - and RELEASES.md names the early ones that predate that chain rather than counting them in - and the build is reproducible from the tagged commit by anyone who wants to carry it on. Zoost being abandoned would cost you the tool. It would not cost you the work you did with it.

Before you start

Two things that will stop you, and it is cheaper to find out now than at the last step.

Your browser may not allow it

Loading an unpacked extension requires Developer mode in chrome://extensions. On a Chrome managed by your organisation, policy can disable that switch or block unpacked extensions outright, and there is no way around it from this side. If the toggle is greyed out or the page says your browser is managed, this is a conversation with whoever administers it, not a thing you can do yourself.

Chrome also shows a "Disable developer mode extensions" prompt at startup while one is loaded, on some platforms every time. It is a warning about the mechanism, not about this package, and dismissing it leaves the extension running.

It will not update itself

An extension loaded this way is frozen at the version you unzipped. It will not follow later releases, and it will not switch itself back to the Store build when the queue clears. Going back is two clicks, but nothing will remind you to.

What you lose, and what you keep

This is the part that surprises people, so it is worth reading before rather than after.

Chrome identifies an extension by an id. The Store build's id comes from the key Google holds; an unpacked build's id is derived from the folder you loaded it from. They are different ids, so to Chrome they are two different extensions, and an extension's stored settings belong to its id.

The unpacked copy opens as if freshly installed. No working folder, no AI provider or API key, no passphrase, no diagram defaults. Nothing is broken and the fix is not failing: it is a different id, so it has its own empty storage.

What you keep is everything that matters. The mirror is files in a folder on your disk and no extension owns it. Point the new copy at the same working folder with Choose folder, grant access again, and every workspace, every pulled function and every bit of history you committed is there, exactly as it was. The re-setup is the folder, and the AI key if you use one. A couple of minutes.

Because the id follows the folder path, moving or renaming the unpacked folder later gives it a new id again and empties its settings a second time. Unzip it somewhere you are content to leave it before you load it, not into Downloads.

The two ids being different has one advantage worth using: the Store build and the unpacked one can be installed at the same time. Leave the Store one in place, so going back is removing the unpacked copy rather than reinstalling anything. Run one at a time, though, and the way to do that is the toggle in chrome://extensions: switch the Store copy off rather than uninstalling it, and it keeps its settings and comes back with one click. Two copies watching the same Zoho tab is not a case anything here was designed for, and on Zoho CRM it is not merely untidy: the hook Zoost puts into the page's own world is guarded so that whichever copy loaded first wins, which leaves the behaviour depending on load order rather than on the copy you meant to use.

Running it

  1. Download the package from the release above, or from the releases page. It is the file named zoost-<product>-<version>-store.zip. Take the one attached to the release; do not build your own, because then none of what follows means anything.
  2. Check it is what it claims to be, if you want to. This is the whole reason the release chain exists, and it is one command with the GitHub CLI:
    gh attestation verify <the zip> --repo ivannot/zoost
    It answers whether that exact file was built by this repository's public workflow from the commit it names. The nerd page has the longer version, including how to compare the hash by hand.
  3. Unzip it into a folder you will keep. The archive has the manifest at its root, which is the layout Chrome wants, so the folder you unzip into is the folder you load.
  4. Open chrome://extensions and turn on Developer mode, top right.
  5. Click Load unpacked and select that folder. The extension appears in the list with an ordinary card, and its side panel opens the way it always did.
  6. Point it at your working folder and re-grant access, as described above. Then carry on.

If Chrome refuses the folder, the usual cause is having selected the one containing the unzipped folder rather than the unzipped folder itself. Chrome wants the directory with manifest.json directly inside it.

Going back

When the Store catches up - this page says so, if you come back and look:

  1. Open chrome://extensions and Remove the unpacked copy.
  2. If you left the Store build installed, it is already there and already current. If you removed it, install it again from Zoost CRM or Zoost Analytics, and point it at your working folder once.
  3. Turn Developer mode back off, so Chrome stops asking.

Nothing needs cleaning up beyond that. The unpacked folder can be deleted; your mirror is somewhere else entirely and is not touched by any of this.

What this is not

It is not a beta channel. The package is the same one submitted for review, not an earlier or looser build. There is no separate branch of Zoost that gets released here first.

It is not a way around the review. The tag builds the package and puts it on the item as a draft; submitting it for review is a separate press, and it appears on the Store when it clears. What this page removes is your wait, not the review.

It is not the supported way to install Zoost. The Store build updates itself, keeps its settings and does not make Chrome nag. If you are not currently blocked by something, install it from the Store and close this page.

It is not a support channel. If something is broken and there is no release ahead of the Store, the fix has not been released yet. Opening an issue is what starts one, and reading the issues already there is how you find out whether the break is known.
