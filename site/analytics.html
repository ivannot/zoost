Hundreds of views, and no way
to see the shape of them. This draws you the map.

Zoost Analytics mirrors a workspace into plain files on your disk — every view with its type and folder, the columns and data types of every table, the foreign keys between them, and the SQL behind each query table as a file of its own. Then it shows you the ER diagram, what reads from what, and what nothing reads any more. It calls no endpoint that creates, edits or deletes anything in Zoho Analytics, and it never reads the rows in your tables.

Why it exists

A workspace outgrows its author

A few years in, a workspace is hundreds of views: tables, query tables holding SQL somebody wrote at 2am, and reports built on reports. Zoho Analytics will answer what one view depends on, one view at a time. It will not tell you the shape of the whole thing.

A history for everything you pulled

Zoho Analytics keeps no history of anything: change a query table's SQL, a column or a relation and the previous state is gone. The mirror is ordinary files, so with Git git diff answers what changed in this workspace last month — the question that matters most the day a number moves and nobody knows why. Git is optional: without it the mirror is still ordinary files you can search and hand over.

The SQL is the source

Tables are schema and reports are configuration, but a query table's SQL is code somebody wrote. It lands as one .sql file each, so it can be diffed, reviewed and searched like the code it is.

Before you delete anything

Asking Zoho Analytics what depends on a view, three hundred times by hand, is how the question never gets asked. Zoost asks it once for everything — and calls the answer a candidate, because a shared link or a scheduled export is invisible to that graph.

What you built, and what Zoho put there

Half the tables in a connected workspace arrived by sync and were never yours. Zoho Analytics' own ER model knows which, and the view list marks them — so the inventory is of your work, not of everything.

What's inside

Local mirror, Git-friendly

  • One pull writes the census, the structure, the relations and the lineage to disk.
  • One .sql file per query table, named after it — the diffable part.
  • One working folder, a subfolder per Zoost product, one folder per workspace inside it.
  • A workspace is identified by its id, not by its folder name: rename either and nothing is orphaned.
  • Give a workspace a name of your own — Zoho Analytics calls the first workspace of every account the same thing, so the list can be several projects with one label. Your name is shown; the platform's is kept beside it, because a list you cannot check against Zoho Analytics is not worth having.

Every view, in one list

  • All of them with type, folder, owner, column count and dates.
  • Search inside columns: type a column name and find the tables that carry it.
  • Design and data told apart: when the design last changed, and when the data last refreshed. They are different facts and the list shows both.
  • Sort by name, type, folder, owner, when the data changed — or by how many views read from it.

Structure, including for reports

  • Every table and query table with its columns and Zoho data types.
  • A report or a pivot has no columns of its own — so Zoost follows what it is built on and shows that structure, saying whose it is rather than passing it off as the report's.
  • Foreign keys on every column, in both directions: what it points at, and what points at it. Each one is a link that opens the other table.

ER diagram that stays readable

  • Tables as boxes, relations as arrows, the join written on the arc exactly as Zoho writes it.
  • Focus one table and walk the graph by clicking; adjustable depth.
  • Click an arc to isolate one relation and push everything else back.
  • Spacing, spread and label size are live sliders. Save PDF for wall-size prints.
  • A relations table too: one row per join, searchable, copyable.

The SQL of your query tables

  • Read it in the panel, and on disk as files you can grep.
  • Search across every query at once.
  • Each one records the source tables it reads and which of their columns it involves — so "if I drop this column, what breaks" has an answer.

What nothing depends on

  • Zoho Analytics' own dependency answer, asked for every view instead of one at a time.
  • For any view: what it reads from, what reads from it, and the dashboards it appears on.
  • Candidates, never a verdict. A shared link, a scheduled export, an embedded report or an API consumer is invisible to that graph, and the number says so.

Health, without a score

  • Views nothing depends on, tables in no relation, views with no description, items that could not be read.
  • Counts and lists. No thresholds, no red flags, no grade.
  • Every figure states what it does not cover, next to itself.

Exports you can hand over

  • The whole workspace as one self-contained HTML file, or as Markdown.
  • A dialog decides section by section what the file may contain; the SQL is opt-in and flagged.
  • The Markdown carries the constraints of Zoho Analytics' SQL dialect too, so an assistant that has never seen Zoho Analytics does not write queries that cannot run.

Optional AI, your own key

  • Anthropic (Claude) or OpenAI (ChatGPT) — the two that are tested, and the only two the extension can reach.
  • With Claude it explores the local mirror itself: reads a structure, follows a foreign key, opens a query's SQL, searches columns, says what depends on what. Every tool call is shown.
  • It is told what Zoho documents about query-table SQL — SELECT only, quoted identifiers, no correlated sub-queries, non-recursive CTEs — so what it writes is a draft to paste, not plausible SQL that fails.
  • It is also told what it cannot know: Zoost never reads your rows, so the assistant has structure and never values.
  • Your key stays in your browser and goes only to your provider — and it can be protected by a passphrase you choose, so what sits on disk is ciphertext. Off by default, because on a personal machine it buys little and on a shared one a lot.

What it does not do

It calls no write endpoint

No creating, editing or deleting a view. One endpoint it calls is a POST whose URL contains CREATE — ZDBCreateERD.ma, the call that returns the workspace's ER model. It computes; it does not create. It is named here because anyone checking the claim will find it. Zoho Analytics is where you build; this is where you look at what you built.

It never reads your rows

Structure, relations, SQL and metadata only. The endpoints that return cell values exist, and are deliberately not called — which is also why the AI assistant can never tell you what is in the data.

Report definitions are not covered

Which columns a chart puts on which axis, and how it aggregates them, would come welded to the computed series — your data. So that endpoint stays unused and this gap stays stated.

It does not validate SQL

Zoost never runs, checks or deploys a query. What the assistant writes is a draft; Zoho Analytics is the only thing that can tell you it compiles.

Relations are Zoho Analytics' own

The foreign keys come from the ER model Zoho Analytics itself draws. What that model does not draw, Zoost does not know — and does not invent.

What this rests on, and what that means for you

Undocumented interfaces

Zoho Analytics publishes no API for most of what Zoost reads. It uses the same internal endpoints the product's own web interface uses, through the session you are already signed in to. One of them is named CREATE in Zoho's own URL scheme and is a POST — it is the call that returns the workspace's ER model, and it computes rather than creates. It is named here rather than left for a reader to find, because a reader will find it.

Which means it can break

Those interfaces carry no compatibility promise. Zoho can change one without notice and a feature can stop working from one day to the next. This is not a hypothetical risk to be discovered later: it is the foundation the tool stands on, and you should know it before you build a process around it.

What is promised, and what is not

Nothing is guaranteed — the licence says so and so does this page. What is offered is effort: a break will be looked at and fixed where fixing it is possible. Sometimes it will not be, and then the feature will say plainly that it cannot do the thing rather than guess. The mirror already on your disk keeps working either way; it is ordinary files.

Read it before you trust it

All of the above is visible in about twenty files of plain JavaScript. Every network call the extension can make is in them, and there is no bundler or minifier between what is published and what you read. If any of this is disqualifying for your organisation, it is better found here than after installing.

How to check we are telling the truth

Read what ships

Around twenty files of plain JavaScript and HTML. No bundler, no minifier, no dependencies — what you download is what runs, and there is no build step that could put something in the package that is not in the repository. You can read all of it in an afternoon.

Built in public, not on a laptop

Pushing a release tag makes GitHub check out that commit, build it twice to prove the result is byte-identical, and sign a provenance statement for the archive. The archive attached to the Release is the file submitted to the Store. The build log is public.

Verify it yourself

gh attestation verify <file> --repo ivannot/zoost asks GitHub whether it built that exact archive. tools/verify.sh rebuilds it on your machine and compares. Neither asks you to trust us.

What none of it proves

Uploading to the Store is a manual step, so no signature covers it: what is proven is how the release archive was built. Google also repackages and re-signs every extension, so what it serves is not byte-identical to what was uploaded. Both are settled at the far end, by diffing the installed extension against the tag. And an attestation says who built a file, never that the file is good — that part is still reading the code.

The record of every submitted version — commit, tag and the SHA-256 of the uploaded package — is in RELEASES.md, including the two entries it says it cannot verify and why.

Get started

  1. Install it. From the Chrome Web Store. Submitted to the Chrome Web Store and in review. Until it is published, clone the repository and load apps/analytics unpacked from chrome://extensions.
  2. Set a working folder — the same one your other Zoost uses, if you have one. Each product keeps its own subfolder inside it.
  3. Open a workspace in Zoho Analytics. The panel takes the workspace from the tab you are on; there is nothing to configure and nothing to pick wrong.
  4. Press + Workspace, then Pull all. A few hundred views take under a minute.
  5. Optional: git init in the workspace folder, and from today you have a history. Everything else works without it.

Everything runs in your browser, using the Zoho session you are already signed into. No server, no account, no telemetry. The only thing that ever leaves your machine is what you choose to send to an AI provider, and never the rows in your tables.
