How to use Zoost - workbench for Zoho Analytics

Zoost - workbench for Zoho CRMZoost - workbench for Zoho Analytics

Short and practical. It assumes you build reports in Zoho Analytics and know your way around a filesystem. Ten minutes gets you from install to a versioned mirror of a workspace.

0. Does anything leave my computer?

No, with one exception you switch on yourself. Zoost has no server and no account. What it reads from Zoho Analytics is written straight to a folder on your own disk and stays there. Nothing is sent to the developer, and there is no analytics or tracking of any kind.

The exception is the AI assistant, and it is off until you paste in your own API key. Once you enable it, what it needs to answer you is sent from your browser directly to the provider you chose - Anthropic or OpenAI - and to nobody else. If your organisation does not allow that, leave it off: everything else works exactly the same. The privacy policy lists what is stored, where, and why.

1. The mental model

Three things, and the rest follows.

Working folder One folder on your disk that you choose once. Everything Zoost writes lives inside it, and each Zoost product keeps its own subfolder, so one folder can serve them all.
Workspace One folder per Zoho Analytics workspace, inside analytics/. Its identity is the workspace id written in .zoost.json, never the folder name - rename either and nothing is orphaned.
The active tab decides The panel takes the workspace from the URL of the tab you are on. There is nothing to pick and nothing to pick wrong. Move to another workspace and every Zoho-bound action is disabled until the tab and the folder agree again.

Zoost only ever reads from Zoho Analytics. It never creates, edits or deletes a view, and it never reads the rows inside your tables - the endpoints that return cell values exist and are deliberately not called. The worst it can do to your workspace is nothing. One of the calls it makes is a POST whose URL contains CREATE - that is Zoho's own name for the request that returns the ER model, and it computes rather than creates. Said here so that finding it does not look like a discovery.

2. First run

  1. Install from the Chrome Web Store and open a Zoho Analytics tab.
  2. Click the Zoost icon to open the side panel.
  3. 📁 Set working folder… - pick one folder. The browser asks for permission; it is the only way an extension may write files, and it applies to that folder alone.
  4. Open the workspace you want to mirror. Its URL looks like analytics.zoho.eu/workspace/1234567890.
  5. + Workspace - creates the folder for it and reads its name from Zoho Analytics.

+ Sample is the other way in, and it needs no Zoho Analytics tab: it writes a workspace of invented data into the working folder so you can open the view list, the ER diagram and the exports before pointing Zoost at anything of your own. It is generated, never fetched - the workspace bar says so, and everything that would talk to the platform is disabled for it. It is an ordinary folder otherwise: delete it with 🗑 like any other. The button disappears once one exists.

The same action is on the Not on a Zoho tab screen, as + Sample workspace: a sample owes the platform nothing, so it opens and reads without a tab and without an account. That screen is where somebody who has just installed Zoost actually is. Once one exists that button reads Open sample workspace and opens it; before Chrome has given the panel access to the working folder it cannot tell, so it says neither and reads just Sample workspace - clicking asks for access first and then does whichever is right - the overlay covers the workspace list, so hiding it there would leave the sample unreachable.

The bar under the toolbar is the guard. Green means the tab and the folder are the same workspace. Amber with a bar of actions means they are not, and everything Zoho-bound stays disabled until you pick one of the two ways out it offers.

Naming a workspace

The name in the workspace list comes from the platform, and the platform is not always helpful: Zoho Analytics names the first workspace of every account the same way, so two projects can arrive on disk looking identical. The ✎ Name this workspace button next to the list gives it a name of your own, and 🗑 Remove workspace beside it deletes that folder - the local mirror only, never anything in Zoho, and a pull brings it back.

It is shown instead of the platform's name, and the platform's name never goes away: it stays in the list's tooltip and in the bar underneath, which always states the real workspace or org the folder is bound to. That is deliberate - the name is your convenience, the identity is Zoho's, and a list showing only your own words would be one you could not check against Zoho. The name is stored in the workspace's own .zoost.json, so it survives a re-pull and travels with the folder. Clear the field to go back to the platform's name.

3. Pulling

Pull all reads the whole workspace in one pass: the list of views, the columns and types of every table and query table, the relations between them, the SQL of each query table, and the dependency graph. A few hundred views take under a minute.

Three toolbar controls are drawn as marks rather than words - Pull all, Pull and ER diagram. The name has not gone anywhere: it is the tooltip, and it is what a screen reader announces. This guide shows the mark next to the name throughout.

Two kinds of failure, told apart on purpose:

  • A stage - the view list, the structure, the ER model - is one call. If it does not answer there is no partial result worth keeping, so the pull stops and nothing is written. What was on disk stays as it was.
  • An item - one view's SQL or lineage - is one call each. One unreadable view must not cost the other four hundred, so failures are collected, the pull finishes, and the status line says how many were missed. Retry N failed appears and re-reads exactly those.

To re-read a single view, open it and use Pull in the detail pane. The ↻ button next to it is local: it reloads the mirror from disk, or re-grants folder access. It never talks to Zoho.

4. Putting it under Git

In the workspace folder:

cd <working folder>/analytics/<workspace>
git init && git add -A && git commit -m "initial mirror"

What you get on disk:

views.jsonthe census: every view with type, folder, owner, dates, tags
schema.jsoncolumns and data types per table, plus the relations
lineage.jsonwhat reads from what, both directions
sql/*.sqlone file per query table - the diffable part
sql/index.jsonid-to-file map, and which source columns each query involves
export/the reports you generate

The .sql files are the point. They are the only thing in Zoho Analytics that is genuinely source somebody wrote, and one file each is what lets git diff answer what changed in this workspace last month - a question Zoho Analytics cannot answer at all.

5. Reading the workspace

The list is every view. Above it, two picklists: Type filters by kind and carries the count of each, Sort orders by name, type, folder, when the data changed, how many views read from it, or owner.

The search box looks at names, folders and column names. Type a column name to find which tables carry it - useful before going looking for where some data lives.

The Cols column counts columns, and a number in brackets means the view has none of its own: only tables and query tables carry columns, so a report or a chart shows the count of the view it is built on, and the tooltip names it. The brackets exist because a count is read as a figure - anything fused to the digits would change what they say.

Two date columns, and they are different facts:

  • Data - when the data last refreshed. Always a real timestamp, always sortable.
  • Design - when the design last changed. A real date for tables and query tables. For reports and dashboards Zoho Analytics only gives text in your interface language, so it is shown exactly as it sends it, in italics, never parsed, and sorted last. Reading a localized date is the same mistake as reading a localized button label.

Rows marked system were put there by Zoho - synced from a connected source rather than built by you. Zoho Analytics' own ER model knows which; the view list does not.

6. Structure and foreign keys

Click any row to open the detail pane. Drag the bar above it to resize; the height is remembered.

Columns shows every column with its Zoho data type. Tables and query tables carry their own; a report or a pivot carries none, so Zoost follows what it is built on and shows that structure - saying whose it is, rather than passing it off as the report's.

The References column is the foreign keys, in both directions, because a lookup is not symmetric:

  • → this column points at another table
  • ← another table's column points at this one

Each is a link: click it and you are looking at the other table. They come from the ER model Zoho Analytics itself draws, with the join written exactly as Zoho writes it.

7. The ER diagram

ER diagram opens the whole workspace in its own window; the same button in a table's detail pane opens the same window focused on that table, at depth 2.

  • Tables as boxes, relations as arrows, the join written on the arc.
  • Click a box to re-centre on it. The Focus group beside the tabs is where that context lives: the table's own name, Everything, the depth that decides how far out from it to go, and ✕ to forget it. It sits with the tabs because it belongs to the window rather than to one view: Explorer sets it, and both the diagram and Relations follow it. Everything pauses the focus rather than dropping it: the name stays on screen and one click picks it up again.
  • Click an arc to isolate one relation and push everything else back - the cheapest way to read a crowded diagram.
  • Fit frames the whole drawing in the window, and a window resize does it for you - unless you have panned or zoomed, in which case the view you chose is kept and Fit hands it back. Layout ⚙ exposes spacing, spread, ring radius, label gap and label size as live sliders. There is no single right value across graphs, so the trade-off is yours to make. The starting values live in ⚙ Settings, and the two are the same setting seen from two places.
  • In Explorer, the tab on the edge of the list - ◂ Hide the list - folds it away so the detail gets the whole window; ▸ Show the list brings it back. Drag the same edge to make the list wider or narrower instead. Per window, not remembered, and only there: the other two views have no list.
  • The first switch to the ER diagram computes the layout, which takes a moment on a large workspace and says so with a spinner and the node count. It is computed once per set of views, so coming back is instant, and narrowing what is drawn computes it again for what is left rather than leaving the boxes where a bigger drawing had put them. The same set is laid out the same way each time.
  • The chips above the tabs are the filter and the colour key at once, grouped by what they ask: Views is which kinds are on screen and every one of them starts on, so switching one off removes it; Only narrows to tables that are also a hub, an orphan or a system table, and starts empty. ↺ All puts everything back and None empties it so one click brings back the kind you want. Each is absent when it would do nothing.
  • Switching a kind off removes what it strands as well: a table whose only relations went into it has nothing left to link it, so it is not drawn, and the status line says how many. They stay in the Explorer list - the diagram is answering a narrower question than the list is.
  • Save PDF prints it at wall size.

The window also has a Relations tab: one row per join, searchable by table, column or join, and every join copyable.

8. Query-table SQL

The SQL tab shows the source of a query table. The Lineage tab lists the source tables it reads and how many of their columns it actually involves - which is what makes if I drop this column, what breaks answerable.

On disk every query is its own file, so grep and git log -p work on them like any other source.

Zoost never runs, validates or deploys SQL. It reads it and writes it to disk; Zoho Analytics remains the only thing that can tell you a query compiles.

9. What nothing depends on

The pull asks Zoho Analytics its own dependency question for every view. The Read by column is how many views read from it plus the dashboards it appears on - click the number to open the breakdown. Pick Nothing depends on in the Type filter to see only the candidates.

Candidates, never a verdict. Zoho Analytics only knows what its own views read from each other. A shared link somebody bookmarked, a scheduled export, an embedded report or an API consumer is invisible to that graph. Treat the list as a place to start asking, not a delete queue.

10. Health

♥ opens the audit in the panel: views nothing depends on, tables in no relation at all, tables Zoho put there rather than you, views with no description, and anything that could not be read in the last pull.

Counts and lists - no thresholds, no red flags, no score. A table in no relation may be a deliberate lookup list; a view nothing reads may feed a scheduled export. Every figure states what it does not cover, next to itself.

11. Exports

HTML (Export HTML) produces one self-contained file with everything the panel shows. MD (Export Markdown) produces the same shaped as context for an AI tool that has never seen your workspace.

A dialog decides section by section what may go in - views, structure, relations, SQL, lineage, health - with Everything and Share-safe presets. The SQL option sits indented under Structure because it depends on it, and it is flagged every time: it is the part somebody wrote.

Both land in export/ inside the workspace folder, named zoost-<workspace>-<timestamp>, so a folder of them sorts into the order they were taken.

The Markdown carries one thing the HTML does not: the constraints of Zoho Analytics' SQL dialect, so an assistant reading that file does not write queries that cannot run.

12. AI assistant & API keys

It also knows this extension. Ask it "how do I export this?", "what happens when I press Health?" or "can this change anything in Zoho Analytics?" and it answers from the panel, without sending you anywhere. Write to it in whatever language you like and it answers in that one. It is told what the buttons do and what the extension will not do; if it does not know, it says so and points at this page rather than inventing a step.

Optional, and off until you configure it. ⚙ Settings → pick a provider, paste a model name and your own API key.

Anthropic (Claude) - full agent

Runs with read-only tools over your local mirror: it reads a structure, follows a foreign key, opens a query's SQL, searches columns and says what depends on what, choosing for itself which to use. Every tool call is shown in the chat, so you can see what it looked at before answering.

OpenAI (ChatGPT) - single-shot

Answers in one pass from the workspace index and the view you have open. It cannot go and read anything itself, so it will tell you what it is missing rather than fetch it.

Anthropic (Claude)OpenAI (ChatGPT)
ModeAgent with read-only toolsSingle pass
What it seesWhatever it decides to open: any view's structure, foreign keys, SQL and lineage, plus column and SQL searchThe workspace index and the view currently open
ProgressEach tool call appears in the chat as it happensA "thinking…" indicator until the answer arrives
Best for"What reads from this table?", "is there already a query joining these two?"Focused questions about the view in front of you

Which one to choose

Claude for anything that needs looking around - "what reads from this table", "is there already a query joining these two" - because those take several lookups. OpenAI is fine for questions about something you already have open. These two are the only providers supported, because they are the two that are tested and the only two the extension may reach.

Removing a key, and switching engine

Each provider block has a Forget button: it empties the model and the key, and the removal takes effect when you press Save AI settings. It is the one place where an empty field means erase - everywhere else an empty key field means "keep what is stored", which is what stops an unrelated save from wiping a key you cannot retype because it is encrypted. Forget is also the way out if you have lost the passphrase.

The Engine selector will not move to a provider that has no model or no API key: it says which is missing and stays where it was, rather than leaving you with an assistant that fails at the first question. Each option also states whether it is ready, so the one selected on a fresh install does not read as a working choice, and a save that leaves exactly one usable engine selects that engine and says so. Both providers' fields are on the same page, so filling them in and picking again is two steps, not a dead end.

Protecting the API key with a passphrase

By default the key is stored in clear text in the browser's extension storage. That is not an oversight and it is not fixable in general: Chrome gives extensions no encryption at rest and no credential store, so a key the extension can read on its own is a key anyone with your browser profile can read. Encrypting it with a secret kept beside it would look like protection and provide none.

The one real protection is a secret the extension does not hold, so ⚙ Settings → AI assistant offers Protect the API key with a passphrase. Turn it on and choose one: the key is encrypted with it (PBKDF2-SHA256, then AES-GCM-256, both from the browser's own cryptography), and what remains on disk is ciphertext. The first time you use the chat after starting the browser, the panel asks for the passphrase and offers Unlock; the key then stays available in memory until the browser closes.

Once it is set the fields go away - the passphrase is not stored, so there is nothing to show in them - and the section says the key is encrypted, with a Change passphrase button when you want a different one.

Three things ask for the passphrase you are already using: changing it, replacing the API key, and turning the protection off. They look different and are the same fact - the stored key has to be decrypted before it can be written again - and Zoost checks what you type against the stored key before saving anything, so a mistyped passphrase cannot leave you locked out of a key you believe you know.

If you lose the passphrase, the section offers Remove the protection. It says what goes and what stays before it acts: the encrypted key is removed and the protection turned off, your model names and every other setting are kept, and you paste the API key in again from your provider's dashboard. Nobody can decrypt that key without the passphrase, Zoost included - this is the only way out, and it is a button rather than a sequence you have to work out.

You can turn it back off at any time, and the way back is symmetrical: Zoost asks for the current passphrase, because storing the key in clear text again means decrypting it first, and only you can do that. Wrong passphrase or none, and nothing is changed - the encrypted key is left exactly as it was rather than discarded. If the passphrase is lost, the way out is to paste the API key in again.

It is off by default because the trade is yours, not mine. On a personal machine, typing a passphrase once per session buys little. On a shared or managed one it buys a lot. There is no recovery - no hint, no reset, no back door: forget the passphrase and you paste your API key in again and pick a new one, which costs one visit to the provider's dashboard. And note what it does not do: while the key is unlocked it is in the browser's memory, where the browser can read it. What a passphrase protects is the key at rest - a copied profile, a backup, someone else on the same machine.

Keeping the conversation - and the bill - under control

Two settings decide what a question costs. Workspace index is how much of the workspace is described to the assistant with every message - bigger means it knows more names, and it is billed each time. The panel prints the real figure for the workspace you have open, under the chat title, so the number is not a guess. Max tool steps caps how many times it may reach for a tool before answering; 20 is the default and most answers use two or three.

When a workspace is too large to describe in full, what gets dropped is decided rather than arbitrary: tables and query tables are never dropped, because they are the vocabulary needed to write a query or follow a foreign key, and reports go first because the assistant can still find those by name. Whatever is left out is named as left out - so it never concludes a view does not exist because it was not shown one.

The assistant is told what Zoho documents about query-table SQL - SELECT only, double-quoted identifiers, no correlated sub-queries, non-recursive CTEs capped at three, three levels of query-over-query. You can read exactly what it is told in ⚙ Settings. What it writes is a draft for you to paste, never something Zoost has checked.

Keeping the conversation - and the bill - under control

Clear is not cosmetic. The whole conversation is re-sent with every message, so a long thread costs more per question and drags old, irrelevant context into new answers. Clear it when you change subject: you get cheaper calls and sharper replies. With Claude, Max tool steps is the other lever - it caps how many explore-then-answer rounds the agent may take before it must reply.

Using the assistant sends the parts of your workspace it needs - view and column names, relations, and the SQL of your query tables - from your browser straight to the provider you chose. It never sends the rows inside your tables, because Zoost does not read them. Nothing goes to the developer. Check this is acceptable for your organisation before enabling it.

13. When something goes wrong

If the bar under the toolbar is amber, the tab you are on and the workspace folder you have selected are different workspaces, and everything that talks to Zoho Analytics is disabled until they agree. Go to Zoho Analytics ↗ opens the workspace the folder belongs to, or you switch the folder to match the tab.

SymptomCause and fix
Everything is disabled The tab and the folder are different workspaces. The amber bar offers both ways out: take the tab to the mirrored workspace, or move the panel to the one the tab is in.
"Not on a Zoho Analytics tab" The panel acts on the active tab. Switch to the Zoho Analytics tab, or use the button on the overlay.
"No workspace open" You are on Zoho Analytics but not inside a workspace. Open one - the URL must contain /workspace/<id>.
The folder button is amber The browser dropped the permission, which it does between sessions. Click anywhere in the panel to restore it; clicking the button itself asks for authorisation, not for the folder again.
"CSRF token not found" The session is not signed in on that tab. Reload the Zoho Analytics page and try again.
N items could not be read Use Retry N failed. Until they are in, the mirror is short by exactly those, and Health lists them.
A report shows no columns Only tables and query tables have columns of their own. If Zoost cannot reach a data-bearing view through what the report is built on, it says so rather than showing an empty table.
