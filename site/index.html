You built it. It is yours.
And the platform gives you no way to see it whole.

Zoost is a small family of Chrome extensions, one per Zoho product. Each mirrors what you have built inside that product — code, schema, relations, dependencies — into plain files on your own disk, then layers navigation, diagrams, search, audit and export on top of that mirror. None of them writes anything back. Everything runs in your browser.

What every Zoost has in common

Read-only, on purpose

No Zoost writes to Zoho. Not a function, not a view, not a setting. Zoho compiles and validates server-side, and owning a write path would mean owning deployment, conflicts and rollback — a different product. You keep working where you already work.

Plain files, your Git

The mirror is ordinary files in a folder you pick: source, JSON, SQL. Commit it and git diff answers "what changed last month" — a question neither product can answer about itself.

The whole thing at once

Both platforms show you one object at a time. Both Zoosts show you the shape: what depends on what, what nothing depends on, where a name is referenced, and one document you can hand to someone who does not have the extension.

Numbers, never verdicts

Counts and lists, with no thresholds and no score. A long function may be a clean mapping table; a view nothing reads may feed a scheduled export. Every figure says what it does not cover, right next to itself, and the judgement stays yours.

Nothing leaves the machine

No server, no account, no telemetry. The extensions use the Zoho session you are already signed into and write to a folder you choose. The one exception is the optional AI assistant — and only if you configure it, with your own key, sending only to the provider you picked.

One interface, learned once

They are twins. The workspace bar, the environment guard, the dialogs, the button colours, the exports and the diagram controls are the same thing in both, down to the wording. Use one and you already know the other.

Certain, or stopped

No guessing at a platform's private interface. Where a path is not certain, the feature stops with a precise message instead of retrying against an assumption. What a Zoost cannot know, it says it cannot know.

Checkable, not just claimed

Releases are built by GitHub from a tagged commit, twice over to prove the bytes are reproducible, and signed with a provenance statement. The archive on the Release is the file submitted to the Store — and one command tells you whether that is true, without taking our word for it.

Open, and yours to fork

Apache-2.0, no build step, no dependencies, no framework. The source is readable by anyone about to give it access to their data — which is the point, since that is exactly what you are being asked to do.

Built and maintained by one person, with substantial help from Claude — “Claudio”, to me — on design, code and wording. The judgement calls, and the responsibility for the result, are mine.

Get started

  1. Pick the product you want to look at: Zoho CRM or Zoho Analytics.
  2. Install the extension — from the Web Store for CRM, or unpacked from source for Analytics.
  3. Choose one working folder. Each Zoost keeps its own subfolder inside it, so a single folder serves them all and the two never meet.
  4. Open the Zoho tab you want to mirror, create the workspace and pull. Then git init, and you have a history from today onwards.

Zoost never writes to Zoho, so the worst it can do to your data is nothing. What it writes is the folder you chose — and what happens to an export after you have made it is up to you.
