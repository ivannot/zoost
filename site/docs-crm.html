0. Does anything leave my computer?

No, with two exceptions you trigger yourself. Zoost has no server and no account. What it reads from Zoho CRM is written straight to a folder on your own disk and stays there. There is no analytics and no tracking of any kind, and nothing leaves unless you press something: the AI assistant, described below, and Report this problem, which shows you the whole report and sends it only when you press Send.

The first exception is the AI assistant, and it is off until you paste in your own API key. Once you enable it, what it needs to answer you is sent from your browser directly to the provider you chose - Anthropic or OpenAI - and to nobody else. If your organisation does not allow that, leave it off: everything else works exactly the same. The privacy policy lists what is stored, where, and why.

1. The mental model

Three things, and everything else follows from them.

Working folderOne folder on your disk that you choose once. Everything Zoost writes lives inside it.
WorkspaceA subfolder, one per Zoho org, created for you. It holds that org's functions, schema, automations and connections as plain files.
PullThe action that fills a workspace from Zoho. Zoost only reads from Zoho - it never writes back.

Zoost is not an editor. You keep writing Deluge in Zoho, where it compiles and validates. Zoost gives you the map, the audit, and - with Git - a history of the parts Zoho does not version.

2. First run

  1. Open a Zoho CRM tab and open the Zoost side panel (the extension icon).
  2. Click 📁 Set working folder… and choose a dedicated, empty folder. Something like ~/Documents/Zoost.
  3. Click + Workspace. Zoost creates the subfolder for the org in your active tab, named crm/instance[-sandbox]-orgid, and selects it. Each Zoost product keeps its own subfolder inside the working folder, so one folder can serve them all.
  4. Click Pull all.

+ Sample is the other way in, and it needs no Zoho tab: it writes a workspace of invented data into the working folder so you can open the tree, the graph and the exports before pointing Zoost at anything of your own. It is generated, never fetched - the workspace bar says so, and everything that would talk to Zoho is disabled for it. It is an ordinary folder otherwise: delete it with 🗑 like any other. The button disappears once one exists.

The same action is on the Not on a Zoho tab screen, as + Sample workspace: a sample owes the platform nothing, so it opens and reads without a tab and without an account. That screen is where somebody who has just installed Zoost actually is. Once one exists that button reads Open sample workspace and opens it; before Chrome has given the panel access to the working folder it cannot tell, so it says neither and reads just Sample workspace - clicking asks for access first and then does whichever is right - the overlay covers the workspace list, so hiding it there would leave the sample unreachable.

Do not put the working folder in OneDrive, Dropbox or iCloud Drive. You will be creating Git repositories inside it, and file-sync services corrupt .git directories by touching index and lock files mid-operation. On-demand (placeholder) files also break the full-text search. Use a local folder and push to a private Git remote if you want an off-machine copy.

Three toolbar controls are drawn as marks rather than words - Pull all, Pull and the diagram button, Wiring in Functions mode and ER diagram in Modules. The name has not gone anywhere: it is the tooltip, and it is what a screen reader announces. This guide shows the mark next to the name throughout.

Chrome does not keep file-system permissions across side-panel reopens: this is how the browser's File System Access API works for extensions, not a bug. Zoost restores it on your first click anywhere in the panel, so normally you will not notice. If it needs you, the folder button turns amber and reads 🔓 Grant access - one click, and no file picker opens.

Naming a workspace

The name in the workspace list comes from the platform, and the platform is not always helpful: a Zoho CRM instance id is exact without being memorable, and two sandboxes of the same org differ by nothing you would recognise at a glance. The ✎ Name this workspace button next to the list gives it a name of your own, and 🗑 Remove workspace beside it deletes that folder - the local mirror only, never anything in Zoho, and a pull brings it back.

It is shown instead of the platform's name, and the platform's name never goes away: it stays in the list's tooltip and in the bar underneath, which always states the real workspace or org the folder is bound to. That is deliberate - the name is your convenience, the identity is Zoho's, and a list showing only your own words would be one you could not check against Zoho. The name is stored in the workspace's own .zoost.json, so it survives a re-pull and travels with the folder. Clear the field to go back to the platform's name.

While a pull is running, the workspace list and its buttons are off, and picking another workspace is refused with Pull in progress. One operation, one workspace: a pull writes many files over several minutes, and letting the target change under it half-way is how half an org ends up in another org's folder. Wait for the pull to finish - the list comes back by itself.

3. Pulling and syncing

  • Pull all mirrors functions, module schema, layouts, related lists, workflows, schedules and the connections catalogue.
  • Pull (in the mode bar) refreshes only the current type - whichever of Functions, Modules, Workflows, Schedules, Actions or Connections is the active tab - faster when you just changed one thing.
  • Auto-sync while you work: save a function in the Zoho editor and the matching local file updates by itself; create one and Zoost fetches it; delete one and it goes from the mirror. No action needed.
    What this sees is what you do in that tab. A function a colleague creates or deletes elsewhere is reconciled at the next Pull all - Zoost notices what happens in front of it, it is not always in step with the platform.

Layouts and related lists arrive with Pull all or Pull in Modules mode. If the layout matrix or the relation catalogue looks empty, that workspace was pulled with an older build - pull again.

A module with layouts gets a Layout: picker above its field table - All fields (flat) or one layout at a time, with hidden ones marked - and View ↗ beside it opens that layout in Zoho. Zoost shows you what the layout contains; Zoho is where it is changed.

4. Putting it under Git

Nothing is automatic here, on purpose: it is your repository, with your conventions.

cd ~/Documents/Zoost/crm/yourinstance-1234567890
git init
git add .
git commit -m "baseline"

What you get on disk:

functions/<namespace>/Deluge functions as .dg files; Java, Python and Node functions as <name>.files/ projects containing every file Zoho returns. Each function also has a .meta.json sidecar
functions/index.jsonthe census: every function with its namespace, id and where it is wired
modules/one file per module - fields, types, lookup targets, picklist values. In the panel a picklist shows its count and opens downwards on a click, one value per line: forty options on one line made the table scroll sideways with no end
modules/layouts/one file per module, with the sections and the fields on each layout - under the modules they describe
workflows/one file per rule: trigger, criteria, instant and scheduled actions
schedules/, connections/the schedule list and the org's connection catalogue
export/the reports you generate

The mirror preserves every file in Java, Python and Node projects. Open the function once, then use its Files tab - a tree that opens and closes - to move between its code, manifests and nested paths; choosing a file shows it under Code. A Deluge function is one file and has no such tab. Directories and subdirectories are preserved explicitly, even when empty; full-text search includes every file. The call graph, module reads and writes, and connection usage remain a Deluge static analysis; Zoost does not infer those relationships from the other languages yet.

One folder per kind, one index.json inside each, and functions under functions/ so a Deluge namespace can never collide with a folder Zoost creates. Before Zoost CRM 1.13 the namespaces sat in the workspace root and the other folders carried a leading underscore to stay out of their way; a workspace in that shape says so and asks for one Pull all. Nothing is migrated and nothing is deleted for you - the old folders are yours to remove.

From then on, pull, and git diff tells you exactly what changed in the org since last time - including schema changes, because module and layout metadata are stored as JSON.

5. Reading your org

The mode segments switch what the tree lists: Functions, Modules, Workflows, Schedules, Actions, Connections. Select an item and the preview opens below.

Two controls in that row are easy to miss. Name: display toggles between the name Zoho CRM shows you and the API name the code uses - the same function, told two ways, and you need the second when writing Deluge. Functions page ↗ opens Zoho CRM's own function list in a tab and filters it to what you had selected, for when you want to edit rather than read.

Above the list, Type (or Status, or Kind, depending on the tab) narrows what is shown. In Modules it separates Standard from Custom; in Workflows and Schedules it is Active / Inactive, plus Has scheduled actions - the rules with at least one action that runs after a delay instead of immediately. Those rows carry a clock and the count, and the tooltip says how long the delay is; the workflow's own panel shows Last run, the same words the Schedules tab uses for the same fact. Both come from the rule already on your disk, so nothing is fetched to answer "which workflows do not fire straight away".

Not every Zoho user may read every one of these. Access to Deluge or to the connections catalogue depends on your role, and there is no way to ask in advance - so Zoost finds out by pulling. If Zoho refuses an area, the pull says so in plain words instead of showing a status code, nothing is written for it, and its tab disappears rather than sitting there greyed out. The reason, and the date it was asked, are in ⚙ Settings → Tabs, next to an ask again tick. Later pulls skip a refused area on purpose - re-asking an answered question on every pull is a thousand requests for one role change - so ticking that box, and pressing Save tabs, is what puts the area back into the next pull, once. Do it when someone tells you your role has changed. Roles are per org: a workspace that refuses an area says nothing about the next one.

The same page is where you choose which tabs to show at all, and in what order - the panel is narrow, and a type you never look at is only in the way. Each row has a second switch, pull, for the separate question of whether Zoost should ask Zoho for that type at all. Turning a tab off clears it, because most tabs are turned off for an area the account cannot read and pulling it then only produces an error - turn it back on if you mirror a type for Git without browsing it. A pull that skipped something says so.

Excluding a type has a consequence Zoost will not let you walk into: its files stop being refreshed, and six months later a report would carry that chapter looking exactly as current as the rest. So every area records when it was last read. A section whose data is behind the others is unticked in the export dialog, with the date and the reason - you can tick it back on, and the report then carries that date. Both reports state the per-area dates in any case: the fact is yours to weigh, and hiding it would be the one thing worse than an old chapter.

  • The code pane keeps the lines as Zoho holds them and scrolls sideways rather than wrapping; Copy code, at the end of that row, puts the whole of it on the clipboard - the lines as they are, not the highlighting.
  • In a function's code, calls to other custom functions are clickable - jump to the definition, then come back with ◂. So are the rules, schedules and actions under Used in; a custom button has no page here, so its module is offered instead - the link is labelled with where it goes.
  • The preview header shows where a function is wired across the org (blueprint, button, schedule…).
  • It also lists the connections the function uses and who last changed it - click a connection to filter the tree to every function that uses it (no more "find in file" for a connection name).
  • Each function carries its size (lines, code lines, KB) and its outbound calls - invokeurl, zoho.crm.* and the other Zoho service tasks - as a badge in the list and in the preview. Calls are counted outside comments and string literals, so a task named in a comment does not inflate the number. These are counts, not a score: length measures verbosity, not complexity, and every outbound call is work Zoho meters - how to weigh that is your call, not mine. Nothing extra is fetched from Zoho and nothing is stored: it is computed from the sources on disk.
  • Runtime in Zoho ↻, in a function's Details, asks Zoho what that one function did lately. The executions come over the window you pick beside the button - Last 24 hours, Today, Yesterday, Last 30 days, or Dates… for any span between two days, picked from a calendar that will not offer an end before the start, nor a day outside the thirty Zoho keeps - and the table, headed by the window or by the dates themselves, shows when each ran, from what, whether it worked and how many milliseconds it took. Below it is the revision history, which Zoho answers whole rather than by period, with Zoho's own note for each. It is read at the moment you press it and is not part of the mirror: it is not stored, it is not in the reports, and it is one request per function, which is why it is a button rather than something a pull does for three hundred functions. A compiled function has no revision history and the box says so rather than showing an empty table.
  • Live / Draft on a compiled function's row is what Zoho is actually running. Java, Python and Node functions are written, saved and then published, so the source in the mirror can be code the org has never run - and nothing on disk tells the two apart. Draft means never published, Draft + means published with a later edit that is not live, and the detail spells out the publication date. A Deluge function has no such state and the column stays empty for it. Both reports carry it too.
  • Language narrows the list to functions written in one language - Deluge, Java, Python or Node. It appears only when the org has more than one: a workspace that is all Deluge gets no control rather than a menu with one entry in it. The languages offered are the ones this org actually uses, so one Zoho adds later turns up here on its own. It narrows alongside Type rather than instead of it, and the search box searches what the two of them leave.
  • Sort reorders the list by Name (grouped) - the default - or by lines, API calls, language or last modified; the ↑/↓ button next to it flips the direction. Picking a sort sets the direction you almost certainly want - A→Z for names, biggest first for numbers - and you can reverse it. A numeric sort drops the namespace grouping and shows one flat list, with the namespace moving onto each row, because "which are the biggest" is a different question from "what is in this namespace". Functions not downloaded yet have no numbers, so they stay at the bottom either way.
  • The Connections tab turns that around: the whole catalogue, org-wide - see section 8, Connections.
  • Functions in Zoho ↗ opens Zoho's own functions page. It used to type the function's name into their search box - the one thing Zoost ever wrote into Zoho - and it no longer does: the panel navigates to their functions page and lets it decide what to show. Zoost takes you there; every click after that is yours.
  • Find has a scope switch attached to it: in: names matches file names, in: code runs a full-text search across every function source in the org - the closest thing to grep over your Deluge, and something Zoho does not provide. Use it before renaming a field or retiring an endpoint. The .* toggle beside the switch reads the text as a regular expression - JavaScript syntax, case-insensitive, ^ and $ match at each line - and a pattern that does not parse says so instead of answering "no matches". Next to it, ▾ opens your saved patterns - an email address and Zoho's 18-digit record id to begin with - and can save the pattern in the box under a name of yours, right there; the list is yours to add to, edit or empty in Settings. A hit opens the file at its line, and every match is painted inside the source the preview shows - the same search, followed through. One honest limit: a pattern built to backtrack can make the search slow. It runs on your machine, over your files, and nowhere else.
  • On a module, the field table has one column per layout: a dot means the field is on that layout, an amber dot means it is required there. Rows highlighted in cream are fields on no layout - API-only.

The tree takes the keyboard too: click it once, then ↑ and ↓ walk the functions that are on screen - what the search and the type filter have left, never inside a collapsed group - and open each as a click would; Home and End go to the two ends.

The panel keeps a history of the items you open. In the detail pane, ◂ goes back one step and ▸ goes forward. The History button beside AI replaces the main list with the complete sequence, most recent first. It marks the current item and shows when each item was opened, so you can jump directly to an earlier step. The same search box filters this list; Name switches between display and internal names, and Clear empties the history without closing the item you are reading. You can also move through it with Alt plus ← or →. A control appears only when it has somewhere to take you. If your Zoho role does not grant access to an area, Zoost refuses the step and explains why instead of opening an empty list. History spans all tabs, remains available when you close the pane, and is cleared only when you change workspace so that entries from different orgs are never mixed.

6. The diagram

Wiring (in Functions mode) opens how the org is wired - what fires what; ER diagram (in Modules mode) opens modules and their relations. From a module preview, the same button opens the entity-relationship diagram focused on that module.

Which modules a function touches, and which functions touch a module. Open a function and its Details pane lists the modules its code reads and the ones it writes - read out of the calls themselves, so zoho.crm.getRecordById("Contacts", id) is a read of Contacts and updateRecord is a write. A COQL query and the path of a REST url count too. Open a module and the same pane turns it round: which functions read it, which write it. Zoho's own editor does not ask that second question: it shows a module's fields and layouts, not the Deluge that writes to it.
Two limits, and they are on the screen as well as here. A module named through a variable cannot be known, so those calls are counted and reported rather than dropped - which makes every list a lower bound, never a guarantee that nothing else writes there. And a name is only shown when it is a module this org actually has: a word that looks like one and is not says nothing.
In the code itself the module is a link: in zoho.crm.getRecordById("Contacts", id) the name "Contacts" opens the module, the way a call to another function opens that function. Only in that position - a string anywhere else is a string, and which position that is comes from each task's own documented signature: in getRelatedRecords("Campaign_Products", "Campaigns", id) the first name is the relation and it takes you to the module at the other end of it, while the second is the parent module. A task whose signature has not been read is left alone rather than guessed at.

How the arrows are found, and what that cannot see. An arrow between two functions is a namespace.name( written in the caller's source. Comments and text in quotes are set aside first, so a commented-out call does not become an arrow. The function it named may therefore appear in the health audit as having no known callers. This method has four limits. Calls written in another form are not detected. If the namespace in the source does not match the function's actual namespace, Zoost links to the only function with that name and marks the result as a deduction; if more than one function has that name, it reports the call as ambiguous instead of choosing. A call inside a branch that never runs still becomes an arrow because Zoost analyses source code, not runtime execution. A self-call is not drawn as an arrow. In precise terms, the diagram shows where your code names other code.

  • The call graph is not only functions. A workflow or a schedule that fires one is a node of its own, and so is every connection a function reaches - each in its own colour, filterable from the chips. So one picture answers what starts the code, what it calls, and what it talks to outside Zoho. All of it comes from what is already on your disk: a workflow's own JSON says which functions it fires, a schedule's index row names the one it runs, and a function's captured meta lists its connections. A workflow whose file has not been pulled is a node with no measured actions rather than a node with none.
  • The chips sit in the window's header, above the view tabs, so they are there whichever view you are in. They are also the colour key: each carries its own hue and its own word.

    Where they come from. They are grouped by dimension - Functions holds whatever categories your own functions actually have; Workflows, Schedules and Connections one each. A kind with nothing in it gets no chip. They are read off your org rather than listed in the code, so a category Zoho reports that nobody expected is there too, colour and all. A function Zoho gave no category for is no category.

    What they do. They show what is on screen: all lit means everything, one click switches one off. The dashed Only group asks the other question - «narrow to nodes that are also…» - and starts empty, because that is the truth when nothing is chosen; those three apply to functions. Two buttons cover the other direction: ↺ All puts everything back, None switches everything off so one click brings back the single kind you are after. Each is absent when it would do nothing.

    How to read their shape. The rounded ones are what a Deluge function is - its category. The square ones are Zoho objects that stand around it: Workflows, Schedules, Connections. The last three are facts about a node rather than kinds of it.

    Any number can be on at once: within a row they add up, across rows they narrow. ✕ clears them, and there is one in the search box too. They steer all three views, so switching Connections off is how you read a diagram without them - the search box narrows the list only.
  • The diagram button now sits in the workspace bar, between MD and Health ♥, with the other things that open on the whole workspace. It no longer comes and goes with the tab: the window can switch between the two drawings itself, so there is always something for it to open, and only which one follows the tab you are on.
  • The bar at the top of that window carries the name you gave the workspace, if you gave it one - beside the platform's own instance and org, never instead of them.
  • The Wiring / Schema pair beside the title says which of the two drawings is on screen, and switches to the other without going back to the panel. The panel builds it - this window has no access to your folder at all - so the panel has to be open and the folder granted; if it is not, the switch stops and says which.
  • Wiring is not only functions, which is why it is not called that. A workflow or a schedule that fires a function is a node of its own; so is every connection a function uses; so is every automation action - notifications, field updates, tasks, webhooks, including the ones no rule fires, which are the ones worth seeing; and so is every module those rules and actions touch. The chips above the tabs group them: Functions by Deluge category, Actions by kind, then one chip each for Workflows, Schedules, Connections and Modules. Switch a group off and the drawing, the list and Relations all narrow together.
  • What is not in it: a function's own record access. Nothing here reads the Deluge to work out which modules a function touches, so a function is never joined to a module - the modules in this drawing are the ones a rule or an action names. A module that no automation touches is not in it either, and that is a different question, which the Health audit answers.
  • Three tabs. Explorer is a list and a detail pane; Wiring is the drawing - boxes and arrows, each box listing what that function calls or what that module holds; Relations puts the link first instead of the thing, one row per call or per related list, searchable and filterable. Selecting anything in Explorer re-centres the other two on it - Relations included: it then lists the links around that item and says so above the table, and Everything in the Focus group is what widens it back.
  • Under a function's references there is a depth and a Wiring button, which opens that window centred on this function - the same pair the Modules preview has for the ER diagram. It is absent for a function that calls nothing and that nothing calls: one box and no arrows is not a diagram.
  • In Explorer, the tab on the edge of the list - ◂ Hide the list - folds it away so a field table or a source listing gets the whole window; ▸ Show the list brings it back. Drag the same edge to make the list wider or narrower instead. Both are per window and not remembered, and they exist only there: the other two views have no list.
  • The first switch to Wiring computes the layout, which takes a moment on a large org and says so with a spinner and the node count. It is computed once per set; going back to the tab is instant, and changing the filter or the scope computes it again for what is left - the chips do not merely hide boxes, the drawing closes up around what survives, which is the point of switching a category off. The same filter lays the graph out the same way each time.
  • Selecting anything in Explorer sets the focus for all three views, and the Focus group beside the tabs is where that context lives: the item's own name, Everything, the depth that decides how far out from it to go, and ✕ to forget it. It sits with the tabs because it belongs to the window rather than to one view: Explorer sets it, and both the diagram and Relations follow it.
  • Everything pauses the focus rather than dropping it: the name stays on screen and one click picks it up again. Everything plus Save PDF produces a single page the size of the drawing - the wall-poster case. Set Fields: key first or it will be unreadable. Clicking a box in the diagram re-centres the focus there.
  • Emphasis: relations pushes the module boxes into the background and brings the relation names forward.
  • Click an arc to isolate one relation: the two modules light up, everything else fades, and a card appears with the relation's API name and the Deluge call, ready to copy.
  • Fit fits the entire drawing in the window. Resizing the window does the same automatically, unless you have already panned or zoomed; in that case your chosen view is preserved until you select Fit again. The tab shows how many boxes the current filters would draw, so you can narrow the graph before opening it. Above 80 boxes, the count turns amber to warn that the layout may become crowded, but the diagram is still drawn. Above 800, Zoost does not compute the layout by default because it would take several seconds and could freeze the window. You can raise this limit in Settings, or reduce the graph by changing the filters or focus. Double-click an empty part of the canvas to zoom in; the point you click moves to the centre. To hide a branch, select the − where an arc meets a box. The tooltip previews which boxes will disappear, including any that would no longer be reachable; boxes that remain reachable by another route stay visible. A + restores the hidden branch, and focusing a hidden item restores it too. Drag a box to move it. Its arcs disappear while you drag and are redrawn when you drop it. Zoost reports any overlaps, while Re-layout discards your arrangement and starts again. When a filter changes, boxes you moved keep their positions and only new boxes are placed automatically. Save PDF prints the arrangement currently on screen. Layout ⚙ provides live controls for spacing, spread, label gap and label size. There is no single right value: a dense or airy layout depends on what you need to inspect.
  • File ▾ holds what leaves the window. Save PDF prints it at wall size. Save arrangement… writes the arrangement you made - which boxes sit where, which branches you folded - to a plain file, and Load arrangement… puts one back. You name the file, so one diagram can have several readings: one arranged for a presentation, one for chasing a problem. Nothing is restored automatically and there is no list of saved arrangements to manage - they are files, in your folders, under your names.
  • When you load one onto a diagram the mirror has moved on, the diagram of today wins and every loss is counted: a box that is gone drops its position, a box that is new is placed by the layout around what was kept, and a box that was renamed loses its position rather than inheriting a stranger's - a box sitting where a different one used to sit would misstate the shape you built. The status line says what happened, in numbers: 31 where you put them · 4 new, placed by the layout · 2 in the file are gone from this diagram. If everything still matches but the relations have changed, it says that too, because otherwise a clean-looking load would be the only thing you were told. An arrangement saved from another org is refused, and the line names both.

What it will not do: above 800 nodes the free-form layout is not attempted at all - computing it would freeze the window - so Everything says so instead of hanging, and stays on the focus. The Explorer and a focused Wiring stay fast at any org size; use a focus and a small depth.

7. Finding a relation name

The API name of a related list is not the API name of either module. It is a third string, and it is what zoho.crm.getRelatedRecords() requires. This is the single most common way to lose twenty minutes writing Deluge.

Two places give it to you:

  • The module preview, in the side panel. Its detail has three tabs - Fields, Related lists and Details - and the related lists have the middle one to themselves. Click an API name to copy it.
  • Relations tab in the graph window: one row per relation, with the target module, the lookup field or linking module behind it, and the full call. Filter chips hide the system related lists (Notes, Attachments, Tasks…) so only your own relations remain.

8. Actions

What a rule fires. A workflow rule almost never does the work itself: it points at something that exists on its own in Zoho CRM and is reused across rules - an email notification, a field update, a task, a webhook. Zoost mirrors those four as one list under Actions, with a Kind filter, because they answer one question: what happens when a rule fires, and which rules fire this.

A rule also carries what it actually did. Show executions (last 30 days), on the rule's own detail, asks Zoho for how many times it ran in that window and shows the answer under the button. It is a measurement and not a verdict: a rule that fired nothing may be correct and waiting, and a rule that fired a great deal may be doing nothing useful. Zoho keeps thirty days, so that is the window - not a choice of ours.

What makes the list worth having is a fact each of them carries: whether Zoho considers it in use. In a real org roughly half are not - measured on one, 85 notifications of 200, 50 field updates of 97, 27 tasks of 56. Those are candidates, exactly as an orphan function is: Zoho answers for the rules it knows about, and something fired from elsewhere would look identical. The filter for them is Attached to nothing, and the same list appears in the health audit under Wiring.

The columns line up down the list - the module it belongs to, and how many rules fire it - and Sort reorders by Kind, then name (the default), Rules that fire it, Module or Last modified, with the ↑/↓ button beside it flipping the direction. As on the functions list, any sort other than the default drops the group headers and goes flat, with the kind moving onto each row.

Opening one shows what it is made of - the template a notification uses, the field an update writes, the method and URL of a webhook, how many recipients - and underneath, which rules fire it. That link is read from the rules already on your disk rather than fetched: a rule names its actions by id, and until now Zoost resolved only the ones that were Deluge functions.

Two things it does not read. The content of an email template, which is a document rather than a structure: the notification names it, and Zoho is where you read it. And who the recipients are - the count comes back with the rule, the list of people does not, and Zoost never asks for it.

The sender's address is captured, because «which address does this go out as» is the question the list exists to answer. It is your organisation's own address or one of your users', never a customer's.

Whether that address travels is yours to decide, in two places and separately: the export dialog has Sender addresses, off by default, and Settings has Let the assistant see sender addresses, also off. The mirror on your disk keeps it either way - what these decide is whether it leaves the machine.

9. Connections

A connection is the named credential a function uses in invokeurl […connection:"…"]. Zoho lists them in setup, but never tells you which functions actually use one - so nobody dares delete any.

The Connections tab is the org's catalogue, pulled with Pull all. One row per connection, with its connector, its status, and how many functions use it. Open one to see exactly which functions, and click through to any of them.

  • Unused - in the catalogue, referenced by no function. The candidates for cleanup.
  • Disconnected - configured but not currently connected. Anything relying on it is already broken.
  • Not in catalogue - a function calls a connection name the catalogue does not have: renamed, removed, or created in another scope.

The join key is the connection name exactly as written in the Deluge call, so the count is structural - not a text search that also matches comments and strings.

Usage counts only cover Deluge functions in this workspace. A connection can also be used by Zoho Flow, Circuits, widgets or client scripts, which Zoost does not read - so treat Unused as "unused by your functions", a candidate to review, not a verdict.

10. Health audit

Health (♥) lists orphan candidates, unresolved and ambiguous calls, broken automations, and lookups pointing at modules that are not in the workspace. Each section states what it does and does not analyse - client scripts and approval rules, for instance, are outside what Zoho exposes.

Treat every entry as a candidate to review. Nothing is ever deleted for you, and an "orphan" may simply be called from somewhere the API does not report.

A third tab, Size & calls, ranks the longest functions and the ones making the most outbound calls. There is no threshold and no verdict attached: a long function is worth a look, not necessarily a problem, and a short one can still be the dangerous one. The counts are there so you can see where length and API cost concentrate - the reading is yours.

Size & calls used to hold only proxies: how long a function is, how many outbound calls it makes. Those cover every function and cost nothing to compute, but they are a guess at what a function costs. Zoho knows the answer, and Zoost now asks: Pull runtime at the top of the view re-reads only that - what is failing and how often things ran - instead of Pull all, which would fetch the whole org again to refresh one reading. Most run over a month, measured lists the busiest functions over the last thirty days - the window that answers «what does this org actually run», where a day answers «is something failing now». Zoost stores the window Zoho says it counted, in the org's own timezone, rather than the dates it asked for. Most run, measured lists the busiest functions with how many times each actually ran in the last 24 hours, and how much the org spent against its ceiling over the same period. The static rows carry the measured number beside them, so a function that is long and runs two hundred times a day is visible as one thing rather than two.

Two limits, stated because they change how you read it. Zoho answers with the busiest few, not every function, so an absent function means «not in the top list», never «never ran». And it reports how often, not how long: a function that runs constantly is not automatically the expensive one.

10b. What is actually failing

The health audit reads the mirror and finds structural suspects - a function nothing calls, a call that resolves to nothing. Code you have commented out does not count as a call, so a function whose only mention is a disabled line is named here rather than left looking alive. It cannot tell you what broke this morning. Zoho does know, and Zoost reads it: Pull runtime, in the health view, fetches what Zoho reports as having failed, and it is the one thing here read from a system that is running rather than from the shape of what you built.

It shows in the two places a failure belongs, and in no tab of its own - a failure is not a kind of object, it is something that happened to a function. On the function itself, under its callers: how many times it has failed and when it last did. In the ♥ Health view, under Functions: the failing functions Zoho lists, with the reason and its line number, and above them how many runs and how many failures Zoho counted in the last 24 hours. That list is read to its first page, and when the page comes back full the panel and the report say so - a number sitting on its own ceiling looks exactly like the whole truth. Counts, with no verdict attached: a function that fails five times an hour by design is not worse than one that failed once.

Because it changes hourly, the panel says the date it was read rather than presenting it as durable, and so does the export. It is the one chapter of a report that carries its own timestamp.

Two things it does not do, and both are on purpose. It does not re-run a failed execution: that makes Zoho run code that writes to your records, which is the first thing this extension refuses. It offers to open the failures page in Zoho, where the button is, and the click is yours. And it does not read the input of a failed run - Zoho keeps it, and for a REST API failure it holds the request body and the caller's name and email, which are records.

11. Exports

Both exports open a dialog first, asking what the file may contain: functions, source code, module schema, layouts, relations, workflows, schedules, actions, sender addresses, connections, failures, health. The Share-safe preset leaves out the five that carry the most: source code, workflows, schedules, sender addresses and the health audit.

  • HTML (Export HTML) - the whole workspace as one self-contained, cross-linked file. Good for handing to a colleague or a manager.
  • MD (Export Markdown) - the same material, shaped as context for an external LLM.

Both carry everything the panel shows, including each function's size and outbound-call counts (a Size and outbound calls table in the Markdown, columns in the HTML index): a report should never be a lesser copy of what you saw on screen.

An export is a file that leaves your machine. With source code included it contains your whole business logic and any credentials someone hardcoded in a function. Decide deliberately, every time.

Files are written to export/ inside the workspace, named zoost-instance-timestamp.

12. AI assistant & API keys

It also knows this extension. Ask it "how do I export this?", "what happens when I press Health?" or "can this change anything in Zoho CRM?" and it answers from the panel, without sending you anywhere. Write to it in whatever language you like and it answers in that one. It is told what the buttons do and what the extension will not do; if it does not know, it says so and points at this page rather than inventing a step.

Optional and off until you configure it. Open ⚙ Settings (bottom of the panel) → AI assistant. Two providers are supported.

Two settings decide what a question costs. Org index is how much of the org is described to the assistant with every message - bigger means it knows more names, and it is billed each time. The panel prints the real figure for the workspace you have open, under the chat title, so the number is not a guess. Max tool steps caps how many times it may reach for a tool before answering; 20 is the default and most answers use two or three.

When an org is too large to describe in full, what gets dropped is decided rather than arbitrary: the function list is never dropped, because it is the vocabulary everything else refers to, and module and connection names go first because the assistant can still fetch those by name. Whatever is left out is named as left out - so it never concludes something does not exist because it was not shown it.

Anthropic (Claude) - full agent

  1. Go to console.anthropic.com and create an API key. A Claude.ai subscription is not an API key - the developer API is billed separately.
  2. Paste the key and the exact model id from Anthropic's docs.

With Anthropic the assistant runs as an agent with read-only tools: it opens functions, traces callers, reads schemas, looks up a connection and who uses it, and searches code by itself. Every tool it uses is shown in the chat.

It also knows each function's size and outbound-call counts, and can filter by them - so "how many functions are longer than 150 lines?" or "which ones make more than five API calls?" are answered from the numbers, not estimated.

OpenAI (ChatGPT) - single-shot

  1. Go to platform.openai.com/api-keys → Create new secret key. Copy it immediately; it is shown once.
  2. ChatGPT Plus is not API access. Add prepaid credit under Billing on the platform, and set a monthly spending limit while you are there.
  3. Paste the key and the model id.

OpenAI receives the org index plus the function you have open - not your whole codebase - and answers in one pass. It cannot go and read another function by itself, so it will ask you for what it is missing rather than invent it. That is intended, but it is a real difference in capability.

Removing a key, and switching engine

Each provider block has a Forget button: it empties the model and the key, and the removal takes effect when you press Save AI settings. It is the one place where an empty field means erase - everywhere else an empty key field means "keep what is stored", which is what stops an unrelated save from wiping a key you cannot retype because it is encrypted. Forget is also the way out if you have lost the passphrase.

The Engine selector will not move to a provider that has no model or no API key: it says which is missing and stays where it was, rather than leaving you with an assistant that fails at the first question. Each option also states whether it is ready, so the one selected on a fresh install does not read as a working choice, and a save that leaves exactly one usable engine selects that engine and says so. Both providers' fields are on the same page, so filling them in and picking again is two steps, not a dead end.

Protecting the API key with a passphrase

By default the key is stored in clear text in the browser's extension storage. That is not an oversight and it is not fixable in general: Chrome gives extensions no encryption at rest and no credential store, so a key the extension can read on its own is a key anyone with your browser profile can read. Encrypting it with a secret kept beside it would look like protection and provide none.

The one real protection is a secret the extension does not hold, so ⚙ Settings → AI assistant offers Protect the key with a passphrase. Turn it on and choose one: the key is encrypted with it (PBKDF2-SHA256, then AES-GCM-256, both from the browser's own cryptography), and what remains on disk is ciphertext. The first time you use the chat after starting the browser, the panel asks for the passphrase and offers Unlock; the key then stays available in memory until the browser closes.

Once it is set the fields go away - the passphrase is not stored, so there is nothing to show in them - and the section says the key is encrypted, with a Change passphrase button when you want a different one.

Three things ask for the passphrase you are already using: changing it, replacing the API key, and turning the protection off. They look different and are the same fact - the stored key has to be decrypted before it can be written again - and Zoost checks what you type against the stored key before saving anything, so a mistyped passphrase cannot leave you locked out of a key you believe you know.

If you lose the passphrase, the section offers Remove the protection. It says what goes and what stays before it acts: the encrypted key is removed and the protection turned off, your model names and every other setting are kept, and you paste the API key in again from your provider's dashboard. Nobody can decrypt that key without the passphrase, Zoost included - this is the only way out, and it is a button rather than a sequence you have to work out.

You can turn it back off at any time, and the way back is symmetrical: Zoost asks for the current passphrase, because storing the key in clear text again means decrypting it first, and only you can do that. Wrong passphrase or none, and nothing is changed - the encrypted key is left exactly as it was rather than discarded. If the passphrase is lost, the way out is to paste the API key in again.

It is off by default because the trade is yours, not mine. On a personal machine, typing a passphrase once per session buys little. On a shared or managed one it buys a lot. There is no recovery - no hint, no reset, no back door: forget the passphrase and you paste your API key in again and pick a new one, which costs one visit to the provider's dashboard. And note what it does not do: while the key is unlocked it is in the browser's memory, where the browser can read it. What a passphrase protects is the key at rest - a copied profile, a backup, someone else on the same machine.

Keeping the conversation - and the bill - under control

Clear is not cosmetic. The whole conversation is re-sent with every message, so a long thread costs more per question and drags old, irrelevant context into new answers. Clear it when you change subject: you get cheaper calls and sharper replies. With Claude, Max tool steps is the other lever - it caps how many explore-then-answer rounds the agent may take before it must reply.

The assistant is the one feature that sends data off your machine. Deluge source, schemas and workflow definitions go to the provider you configure, under their terms. If your organisation restricts sending source code to third-party AI services, leave it off. Everything else in Zoost is local.

13. Production vs sandbox

Every workspace is bound to one org, host and instance, recorded in its .zoost.json. If the Zoho tab in front of you belongs to a different org, Zoost disables every Zoho-bound action and shows a bar offering to switch tab or switch workspace. This is deliberate friction: it is what stops a sandbox pull from overwriting a production mirror.

Renaming a folder, or renaming the portal in Zoho, does not break anything - identity lives in the org id inside the file, not in the folder name.

14. When something goes wrong

If the bar under the toolbar is amber, the tab you are on and the workspace you have selected belong to different orgs, and everything that talks to Zoho CRM is disabled until they agree. The bar offers two ways out: Switch tab → «instance» ↗ takes the tab to the org the workspace belongs to, or you switch the workspace to match the tab. Nothing is disabled to be awkward - it is the one guard that stops you mirroring one org into another org's folder.

With no Zoho CRM tab at all the panel says so over the whole workbench and offers Go to Zoho CRM ↗. That opens your Zoho CRM home - the account's, not a particular org's - which is the right button after signing out of one org to sign into another. Which data centre that is comes from the workspace you have open, or from the tab.

Beside the button is a picklist of every data centre. After signing out of one org, which org you want next is a choice and nothing here can deduce it: a consultant with clients on .eu, .com and .jp may well want the one they have never opened from this machine. It starts on the data centre this workspace or this tab is on, and otherwise on ⚙ Settings → Data centre, where the default lives.

The footer stays reachable under that screen, so Settings, Help and About are one click away while the rest is idle.

A Save that has something to save says so. Each section keeps its own, and the button lights up - with the words Unsaved changes beside it - only while what is on screen differs from what is stored. Put a change back the way it was and both go, because the question it answers is «is this different», not «have you touched it». Two controls save themselves as you change them, and say so: the data centre and the AI engine, each a single choice with nothing to compose. Everything else waits for its Save.

Settings open in two windows. The settings page is an ordinary tab, so it can be open twice - or open here while the panel writes the same setting. If a section changes elsewhere while you are editing it, that section says so and offers Take theirs, which reloads what was saved, and Keep mine, which keeps what you typed so you can save over it deliberately. Nothing is decided for you and nothing is overwritten behind your back.

Still stuck, or found a bug? When something fails, the panel offers Report this problem: it builds a short report - versions, the error, the last few status lines, counters - and opens a page with it, in a window of its own. Nothing has been sent at that point: the text is in front of you, and Send as a public issue is yours to press or not. The trace is locked, because what fixes a problem is that it is exactly what your browser produced; Edit it anyway unlocks it and the report then travels marked as altered. A second box is yours for anything you want to add. It carries no code and no key at all, and names, paths and ids are stripped wherever they can be recognised. For anything else, or if the problem is a security one, write to ivan@zoost.it, which is private. Zoost is free and maintained in spare time - best effort, no guaranteed response time.
