Your Zoho CRM org as a local,
versionable, navigable codebase. And a map of how it fits together.

Zoost is a Chrome extension that mirrors your Deluge functions, module schema, relations, layouts, workflows, schedules and connections into plain files on your disk — then layers on reference graphs, ER diagrams, full-text search across every function, a relation catalogue, a connections catalogue, a health audit, shareable exports and an optional AI assistant that reads your actual org. Everything runs in your browser.

Why it exists

A history for everything you pulled

Zoho CRM's own version history covers a function, one at a time, inside Zoho. Everything else the pull captures — module schema, layouts, related lists, workflows, schedules, connections — arrives on your disk as plain files, so with Git it gets a history too, and one diff answers what changed in this org last month across every kind at once rather than one function at a time. Git is optional: without it the mirror is still ordinary files you can search and hand over.

The whole org at once

Functions, modules, relations, workflows, schedules and connections in one navigable place, and in one document you can hand to someone who does not have the extension.

Not an editor, on purpose

Zoost does not replace Zoho's editor. You keep writing where Zoho compiles and validates. Zoost is the other half: navigation, cross-references, the map and the audit the editor has no room for — and, with Git, a history of the parts Zoho does not version.

Grep your whole org

Full-text search across every Deluge function at once — the thing Zoho has never had. Find every place a field, a module, an endpoint or a hardcoded id is referenced, before you change it.

The relation names you keep losing

The API name of a related list is neither module's api name — and it is what getRelatedRecords() demands. Zoost catalogues every relation with the call ready to copy.

Built and maintained by one person, with substantial help from Claude — “Claudio”, to me — on design, code and wording. The judgement calls, and the responsibility, are mine.

What's inside

Local mirror, Git-friendly

  • Pull every Deluge function to .dg source plus metadata sidecars.
  • Auto-sync on save: save in Zoho, the local file follows.
  • Functions deleted in Zoho are pruned locally on the next pull, so the folder stays a faithful mirror.
  • One working folder, a subfolder per product, one per org inside it — production and sandbox never mix.
  • Give a workspace a name of your own — an instance id is exact without being memorable. Your name is shown; the instance and org are kept beside it, because a list you cannot check against Zoho CRM is not worth having.

Understand the implementation

  • Reference graph: who calls a function (impact) and what it calls (dependencies), as a searchable explorer and a node-link diagram.
  • Full-text search: one query across every function's source. Switch the search scope from names to code and find every reference to a field, module or hardcoded id in the org.
  • Hypertext code: calls to custom functions are clickable — jump to the definition and back.
  • Reverse usage: where each function is wired across the org — blueprint, button, schedule — read from Zoho's own signal, with no expensive scans.
  • Connections per function: every function lists the connections it uses — click one to filter the tree to every other function that uses it. Structured, not a text search.
  • Authorship: who last changed a function, and when, next to its code.
  • Size & outbound calls: length in lines and KB, and how many invokeurl, zoho.crm.* and other Zoho service calls a function makes — counted outside comments and strings. Counts, not a score; you decide how to read them. Sort the list by any of them to see where length and API cost concentrate.

Schema, layouts and relations

  • Every field with type, lookup target and picklist values.
  • Layout matrix: one column per layout, a dot where a field belongs, amber where it is required there — and fields in no layout flagged as API-only.
  • Relation catalogue: one row per related list, with target module, the lookup or linking module behind it, and the getRelatedRecords() call to copy.

ER diagram that stays readable

  • Modules as tables, foreign keys as arrows. Pan, zoom, fit, save as PDF.
  • Focus any module and walk the graph by clicking; adjustable depth.
  • Relation-first mode: modules recede, relation names take the foreground.
  • Click an arc to isolate one relation and push everything else back.
  • Spacing, spread and label size are live sliders — and an all-modules scope for wall-size prints.

Fits the access you actually have

  • Not every Zoho user may read Deluge or the connections catalogue, and no API says so in advance — so Zoost finds out by asking. An area your role is refused is recorded with the date, nothing is written for it, and its tab is removed instead of sitting there greyed out.
  • The refusal is said in words, not as a status code, and Settings explains it and re-checks. Roles are per org, so another workspace may well grant it.
  • You can hide and reorder the tabs yourself too. That changes the panel only: the mirror, the exports and the assistant still see everything.

Automation map

  • Workflows with triggers, criteria, instant and time-based actions, and the functions they invoke.
  • Which ones do not fire straight away: the count of actions that run after a delay, how long that delay is, and a filter that shows only those rules. Plus the last time each rule ran. Read from the rule already on your disk, not asked for again.
  • Schedules with frequency, status and target function.
  • On-demand workflow execution stats.

Connections catalogue

  • Every connection in the org, pulled from Zoho: its connector, who created it, and its OAuth scopes.
  • Usage count: how many functions use each one — open it to see exactly which.
  • Filter to Unused (no function references it) or Disconnected (configured but not connected) — the two states worth acting on.
  • Connections a function calls but that no longer exist in the catalogue are flagged too.

Health audit

  • Orphan candidates, unresolved calls, ambiguous calls.
  • Size & calls: the longest functions and the ones making the most outbound calls — plain counts, no threshold and no verdict.
  • Broken automations and lookups pointing at modules that are not there.
  • Every check states what it does and does not analyse. Candidates to review — never automatic deletions.

Exports you can hand over

  • HTML: the whole workspace as one self-contained, cross-linked, searchable file.
  • Markdown: the same material shaped as context for an external LLM.
  • A scope dialog decides what may leave your machine, section by section. Source code is opt-in and flagged every time.

AI assistant — bring your own key

  • Two providers, both tested: Anthropic (Claude) and OpenAI (ChatGPT).
  • They are not equivalent, and the chat says which is active: Claude explores the org on its own, OpenAI answers in one pass from the index and the open function.
  • With Anthropic it runs as an agent with read-only tools, so it opens your functions, traces callers, looks up connections and searches your code instead of guessing. Every tool call is shown.
  • Streaming answers, Markdown rendering, a tool-step limit you control.
  • Entirely optional. Keys stay in your browser; requests go straight to your provider — and the key can be protected by a passphrase you choose, so what sits on disk is ciphertext. Off by default, because on a personal machine it buys little and on a shared one a lot.
  • Clear resets the thread — which also trims what is re-sent each time, so it is the main lever on cost.

What this rests on, and what that means for you

Undocumented interfaces

Zoho CRM publishes no API for most of what Zoost reads. It uses the same internal endpoints the product's own web interface uses, through the session you are already signed in to. It also reads two identifiers — your org id and user id — out of the page's own HTML, because no endpoint offers them, and it takes the CSRF token from the cookies your browser already holds. Separately, it watches the Zoho CRM page for one thing only: the URL and method of the request that saves a function, so your local copy can follow. It reads no headers and no response bodies, and alters nothing the page sends or receives.

Which means it can break

Those interfaces carry no compatibility promise. Zoho can change one without notice and a feature can stop working from one day to the next. This is not a hypothetical risk to be discovered later: it is the foundation the tool stands on, and you should know it before you build a process around it.

What is promised, and what is not

Nothing is guaranteed — the licence says so and so does this page. What is offered is effort: a break will be looked at and fixed where fixing it is possible. Sometimes it will not be, and then the feature will say plainly that it cannot do the thing rather than guess. The mirror already on your disk keeps working either way; it is ordinary files.

Read it before you trust it

All of the above is visible in about twenty files of plain JavaScript. Every network call the extension can make is in them, and there is no bundler or minifier between what is published and what you read. If any of this is disqualifying for your organisation, it is better found here than after installing.

How to check we are telling the truth

Read what ships

Around twenty files of plain JavaScript and HTML. No bundler, no minifier, no dependencies — what you download is what runs, and there is no build step that could put something in the package that is not in the repository. You can read all of it in an afternoon.

Built in public, not on a laptop

Pushing a release tag makes GitHub check out that commit, build it twice to prove the result is byte-identical, and sign a provenance statement for the archive. The archive attached to the Release is the file submitted to the Store. The build log is public.

Verify it yourself

gh attestation verify <file> --repo ivannot/zoost asks GitHub whether it built that exact archive. tools/verify.sh rebuilds it on your machine and compares. Neither asks you to trust us.

What none of it proves

Uploading to the Store is a manual step, so no signature covers it: what is proven is how the release archive was built. Google also repackages and re-signs every extension, so what it serves is not byte-identical to what was uploaded. Both are settled at the far end, by diffing the installed extension against the tag. And an attestation says who built a file, never that the file is good — that part is still reading the code.

The record of every submitted version — commit, tag and the SHA-256 of the uploaded package — is in RELEASES.md, including the two entries it says it cannot verify and why.

Get started

  1. Install from the Chrome Web Store and open the side panel.
  2. In Settings, pick a working folder — a dedicated, empty folder. Every workspace will live inside it.
  3. Open a Zoho CRM tab and click +. Zoost creates the workspace for that org.
  4. Click Pull all to mirror functions, modules, layouts, relations, workflows, schedules and connections.
  5. Optional: git init in the folder, and you have the whole org's history from here on. Everything else works without it.
  6. Explore: follow a call, open the graph, run the health audit, or export the lot.

Full walkthrough, including API key setup and troubleshooting: How to use Zoost.

You need to be signed in to Zoho CRM in the same browser. Zoost uses your existing session and your existing permissions — it can see exactly what you can see, and nothing more.

The AI assistant is the one part that sends data outside your machine: the workspace content it needs, including Deluge source, goes to the provider you configure. Check that this is acceptable in your organisation before enabling it. Everything else stays local.
