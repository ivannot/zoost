Zoost CRMZoost - workbench for Zoho CRM

Your Zoho CRM org as a local,
versionable, navigable codebase. With a map of how everything connects.

Every Deluge function becomes a file you can diff. Zoost maps which functions call each other, how modules are related, and when each automation runs. Your whole Zoho CRM org is searchable on your own disk, and Zoost calls no endpoint that creates, edits or deletes anything in it.

Why it exists

A history for everything you pulled

Zoho CRM's own version history covers a function, one at a time, inside Zoho. Everything else the pull captures - module schema, layouts, related lists, workflows and what they fire, schedules, connections - arrives on your disk as plain files. Put them under Git and they get a history too. A single diff can then show what changed in this org last month across every kind of object. Git is optional: without it, the mirror is still a set of ordinary files you can search and share.

The whole org at once

Functions, modules, relations, workflows, schedules, actions and connections in one navigable place, and in one document you can hand to someone who does not have the extension.

Not an editor, on purpose

Zoost does not replace Zoho's editor. You keep writing where Zoho compiles and validates your code. Zoost adds the navigation, cross-references, maps and audit views that the editor does not provide. With Git, it also gives you a history of the parts Zoho does not version.

Grep your whole org

Full-text search across every Deluge function at once - the thing Zoho has never had. Find every place a field, a module, an endpoint or a hardcoded id is referenced, before you change it.

The relation names that are hard to find

The API name of a related list is neither module's API name - and it is what getRelatedRecords() demands. Zoost catalogues every relation with the call ready to copy.

Several orgs, side by side

One working folder, a subfolder per org, and each workspace bound to the org, host and instance it came from. If you consult, four clients stay open at once and none can be pulled into another's mirror: when the tab and the workspace disagree, everything that touches Zoho is switched off until they match. Production and sandbox count as two.

Built and maintained by one person, with substantial help from Claudio on design, code and wording. The judgement calls, and the responsibility, are mine.

What's inside

Every function, as a file

  • Deluge source in namespaced folders, ready for Git. Save, create or delete a function in Zoho and the folder follows while you work.
  • Full-text search across every function at once - the closest thing to grep over your org, and something Zoho does not offer.
  • Each one carries its size, its outbound API calls, who last changed it, and the connections it uses.

The map

  • Graph: who calls a function, and what it calls. Click through it.
  • ER diagram: modules as tables and lookups as arrows. Focus on one module, follow its relations, or print the full diagram at wall size.
  • Calls to other functions are clickable in the code - jump to the definition and back.
  • Which modules a function reads and writes - taken from the calls themselves - and the question turned round: open a module and see which functions touch it. A call that names its module through a variable is counted and declared, so every list is a floor and never a promise.

Relations and layouts

  • One row per related list, with its API name and the getRelatedRecords() call ready to copy.
  • The lookup field or linking module behind each one, so you can see how it is wired.
  • Every field with its type, and a matrix showing which layout it appears on.

Automations, and which ones wait

  • Workflows with triggers, criteria and the functions they invoke; schedules with frequency and status.
  • Which rules do not fire straight away, how long they wait, and when each last ran.
  • The org's connection catalogue, with how many functions use each one - so you can tell what is safe to delete.

What is actually breaking

  • What Zoho reports as failing: the function, what invoked it, the reason with its line number, how often.
  • How many runs and how many failures Zoho counted in the last 24 hours.
  • It does not re-run anything - that would write - and it does not read the input of a failed run.

The health check

  • Orphan candidates, unresolved calls, broken automations, lookups pointing at nothing.
  • Counts and lists. No thresholds, no red flags, no grade.
  • Every figure states what it does not cover, right next to itself.

Exports, and an optional assistant

  • The whole org as one self-contained HTML file, or as Markdown for an AI tool.
  • A dialog decides what may leave your machine, section by section. Source code is opt-in.
  • With your own key, an assistant that reads your org rather than guessing - and can be protected by a passphrase.
  • When the assistant is worth a key, and when the export is the better route.

Get started

  1. Install from the Chrome Web Store and open the side panel.
  2. In Settings, pick a working folder - a dedicated, empty folder. Every workspace will live inside it.
  3. Open a Zoho CRM tab and click +. Zoost creates the workspace for that org.
  4. Click Pull all to mirror functions, modules, layouts, relations, workflows, schedules, actions and connections.
  5. Optional: git init in the folder, and you have the whole org's history from here on. Everything else works without it.
  6. Explore: follow a call, open the graph, run the health audit, or export the lot.

Or press + Sample and skip all of it. It writes a workspace of invented data into the working folder, so you can open the tree, the diagrams and the exports before pointing Zoost at anything of your own. No Zoho tab, no account.

It is generated rather than fetched, everything that would talk to Zoho is disabled for it, and you delete it like any other workspace. What that is worth, and how to evaluate it that way →

You need to be signed in to Zoho CRM in the same browser. Zoost uses your existing session and your existing permissions - it can see exactly what you can see, and nothing more.

The AI assistant is the part that sends your org's content outside your machine: the workspace content it needs, including Deluge source, goes to the provider you configure. Check that this is acceptable in your organisation before enabling it. The only other thing that ever leaves is a problem report you write, read in full and send yourself. Everything else stays local.
