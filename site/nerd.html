Undocumented interfaces

Neither Zoho CRM nor Zoho Analytics publishes an API for most of what Zoost reads. Both extensions use the same internal endpoints the products' own web interfaces use, through the session you are already signed in to.

That has consequences worth knowing before you build a process around either of them.

Reading Zoho CRM

Reads two identifiers - your org id and your user id - out of the page's own HTML, because no endpoint offers them, and takes the CSRF token from the cookies your browser already holds.

Separately it watches the page for one thing: the URL and method of the request that saves a function, so the local copy can follow when you save. It reads no headers and no response bodies, and alters nothing the page sends or receives.

Two token families, and they are not interchangeable: the /crm/ endpoints want crmcsrfparam with the CT_CSRF_TOKEN cookie, the /deluge/ ones want drepn with the drecn cookie. The prefix is not the cookie's name, and assuming it was cost a day: the two usually hold the same value, until one rotates.

Reading Zoho Analytics

Takes the workspace from the URL of the tab you are on - /workspace/{id} - so there is nothing to scrape and nothing to pick wrong. CSRF follows the HTTP method rather than the path: every POST carries X-ZCSRF-TOKEN, no GET does, measured across a 104-request capture with no exceptions.

The ER model comes from one POST to ZDBCreateERD.ma. Its URL contains CREATE, and what comes back is the model - Zoho Analytics' own diagram screen makes the same call. What can be established from here is what Zoost does: one request, and the answer kept on your disk. What a server keeps afterwards is not something a browser extension can prove, so it is not claimed: if that distinction matters to your review, compare the workspace before and after, and your plan's audit trail if it has one. It is named here because anyone checking the read-only claim literally will find it, and finding it unannounced would read as a caught lie rather than as what it is.

Sending a problem report

The one path here that ends in a public place, so it is written out rather than summarised. The panel builds the text, redacts it, and opens this page - through the DOM, never through the address, because a URL is written to your browser history and syncs with it. You read it, you may edit it, and nothing moves until you press Send.

What Send posts to is /api/report, and that endpoint is in this repository - site/_worker.js, the same file that answers the version badge. Reviewers have assumed the server behind it was somewhere unreadable, which is a fair assumption about most sites and wrong about this one. It refuses unless an anti-abuse check passes, rate-limits per address by a salted hash, so nothing this site writes down can be walked back to an address - not even by whoever reads the store. Cloudflare, which serves the page, sees the address the way any host does, and the anti-abuse check is given it because that is what the check is for, redacts the text again on the way through - a client is never believed twice - caps the size, and rebuilds the issue body from validated pieces inside a fence nothing can climb out of. It becomes a public issue on GitHub, under my account, and you get its link.

Certain, or stopped

No retry loops against a guess. No matching a button label that changes with the interface language. No synthetic clicks into a page I do not own. Where a path is not certain, the feature stops with a precise message instead of trying something and hoping.

This is why Zoost CRM's function Go to was removed in 1.1.0: it drove Zoho's editor by clicking a localised "Edit function" label, looped ten times, and then failed with the wrong message. Find in Zoho replaced it - it navigates by constructed URL and filters the list deterministically, and the last, language-dependent click is yours.

The exceptions are narrow, deliberate and written down: a bounded wait for a known element after a navigation, one retry on a genuinely transient failure (network, 429, 5xx and never a deterministic 4xx), and recovery by an action that was measured to work - the first /deluge/ call after a fresh login is refused, any ordinary Zoho CRM call fixes it, and that was reproduced deliberately rather than guessed at.

What is never called

Neither extension calls an endpoint that creates, edits or deletes anything. That is a property of which endpoints are in the source, not something the browser enforces - and the source is about twenty-one files of plain JavaScript for Zoho CRM and thirteen for Zoho Analytics, with no bundler and no minifier between what is published and what you read.

Two Zoho Analytics endpoints are deliberately left alone, and the reason is the same in both cases: they return your data.

  • ZDBTableDataAction.ma returns the actual cell values of a table. Zoost states it never reads your rows, so it does not call it.
  • ZAChartView.ve would give the report definition Zoost otherwise lacks - chart type, groupings, axes - but it comes welded to the computed series, which is your data again. So report definitions stay uncovered, and every surface says so rather than implying the mirror is complete.

Guessing at a parameter to suppress the data is exactly where a read-only claim gets broken by accident. It is not attempted.

What is promised, and what is not

Those internal interfaces carry no compatibility promise. Zoho can change one without notice and a feature can stop working from one day to the next.

Nothing is guaranteed - the licence says so and so does this page. What is offered is effort: a break will be looked at and fixed where fixing it is possible. Sometimes it will not be, and then the feature will say plainly that it cannot do the thing rather than guess. The mirror already on your disk keeps working either way, because it is files you can open in any editor.

How a release is built

Pushing a release tag makes GitHub check out that commit, build it twice to prove the result is byte-identical, print the archive's contents into a public log, and sign a provenance attestation for it. The archive attached to the Release is the file submitted to the Chrome Web Store - never a build from a laptop.

Reproducibility is load-bearing rather than decorative: publishing a SHA-256 is worth nothing if two builds of the same commit differ, and mine did, because zip stores each file's mtime and walks the directory in filesystem order. The build now stamps every file with the commit's own date, sorts the file list, and passes -X.

Every GitHub Action is pinned to a commit hash, never to a moving tag. A supply chain that ends in "and then whatever that tag says today" is not one.

Which is also the answer to a fair question, stated plainly rather than left to be guessed at. This code was written with heavy assistance from a language model and reviewed line by line, and that is part of why the chain above exists in the form it does.

Twenty-one files for Zoho CRM and thirteen for Zoho Analytics, no bundler and no minifier, a build reproduced twice on a machine that is not mine and signed, a hash you can check in one command: none of it asks you to trust how the code was produced. Who typed it is the least verifiable thing about a program, and the least interesting once the rest can be read.

Check it yourself

gh attestation verify <file> --repo ivannot/zoost asks GitHub whether it built that exact archive
tools/verify.sh rebuilds it on your machine and compares the hashes
RELEASES.md commit, tag and SHA-256 of every submitted version - including the two entries it says it cannot verify, and why
llms.txt the same map written for an assistant asked to assess the product rather than summarise the landing page

Neither command asks you to take my word for it. If any of this is disqualifying for your organisation, it is better found here than after installing.

The same two commands are how you check a release you install by hand. If a fix is out and the Chrome Web Store has not caught up with it yet, in case of emergency is the page for that: the same signed archive, run without waiting for the queue.

The same, asked of an assistant

A narrower prompt than the one on the home page, for a reader who is already this far down: it takes the technical claims apart one at a time rather than describing the product. Everything it asks about is in this page, so its answer and this page can be compared line by line - which is the only reason to run both.

Tell me where the technical claims about this project fail.

The code:    https://github.com/ivannot/zoost
             (two Chrome extensions: apps/crm and apps/analytics)
The claims:  https://zoost.it/nerd , README.md, and the description
             field inside each manifest.json

Say first which of those you could open. Answer from the code for
everything the code can settle; if you could not reach the code, stop
rather than answering from what you already know.

1. It says it never writes to Zoho. Find every request that is not a GET
   and say what each one is for.
2. Which hosts can it reach at all? Compare that with what the two
   manifests declare, and with the four Chrome permissions they ask for.
3. What leaves the machine, and under what conditions? The optional AI
   assistant is supposed to be the only exception, and only once someone
   enters their own key.
4. What does it store, where, and what happens to a stored API key when
   the passphrase protection is on and when it is off.
5. How does it tell «Zoho returned nothing» apart from «Zoho refused»
   and from «the response was not the shape this reads»?

Tell me what contradicts those claims, what you cannot decide from the
source alone, and what you would want to test in a running browser.

What none of it proves

The upload to the Chrome Web Store is a workflow reading the Release asset, so the file Google receives is the one that was built and signed; what is still by hand is pressing Submit, which moves no bytes. What is still not covered is the far end: Google repackages and re-signs every extension, so what it serves is not byte-identical to what was uploaded.

That one is settled at the far end, by diffing the installed extension against the tag - the tag of the version you have, which chrome://extensions states.

Mind which tag. Google publishes days after a submission rather than minutes, so the newest tag here is routinely ahead of what the Store is serving, and a version still in review is not being served at all. Diffing against that one gives a mismatch that says nothing about either file.

And an attestation says who built a file, never that the file is good. That part is still reading the code.
